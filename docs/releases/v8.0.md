# Release v8.0

Guard schema 8. The agent no longer runs the guard; it asks the guard to act. Four commands replace the ceremony of v7: `guard run` prices and submits a job, `guard wait` waits for it, `guard ask` puts a question to a person, and `guard status` says what runs, what is blocked and what to do next. The broker writes the run's question card, records each decision, and signs every receipt. A schema 7 project moves once, through `guard init --update`, in a pull request a person merges. This release breaks the compatibility contract once, by the owner's decision; [compatibility.md](../compatibility.md#removed-in-schema-8) lists every removal.

The design is [design-v8.md](../design-v8.md); the experiments behind each choice are named there.

## What changes for the agent

- **`AGENTS.md` is under 150 words.** It names the four commands and the two rules about owned paths and untrusted text, and nothing else. The longer v7 text caused the reads it was meant to prevent (E5).
- **One way to submit.** `guard run runs/<run_id> --why "<sentence>" -- <sbatch options> <script>` checks the job against the card on the protected branch, writes `runs/<run_id>/question.card` on `run/<run_id>`, and submits it. On a host named in `launch_hosts` the same line launches the job under the host supervisor, boxed. A leading `sbatch`, `bash`, `sh` or `srun` after `--` is dropped.
- **Every refusal is two lines.** `H4R-<code> <reason>`, then a command to run as it is. [refusals.md](../refusals.md) lists the codes. `guard/run preflight`, `ripples` and `launch` print H4R-R09 with the `guard run` line for the same job.
- **Over budget means a question, not a refusal.** A job that fits the per-job limits but not the remaining budget is queued as a question for a person (exit 3); it runs if a person says yes before the deadline, and the default answer is no.
- **No agent-written card.** The fence refuses an added `runs/*/question.card` that the broker did not write (H4R-F03), and the agent states no number that enters a decision.

## What changes for a project

| File | Change |
|---|---|
| `guard/budget.card` | `harness: v8.0`; `compute: none`, `holdout_max_submissions: 3`, `ask_deadline: 30m`, `approval: auto` and `broker_key:` appended. Every existing line stays, including keys schema 8 no longer reads. |
| `guard/harness-<pin>.sh` (offline) | the v8.0 bundle in place of the old pin's file |
| `guard/run` | the v8 shim: `fence`, `code`, `manifest`, `receipts-check` |
| `.github/workflows/guard-fence.yml` | fetches `guard/receipts` for the fence's receipt check; name and job unchanged |
| `runs/_template/question.card` | deleted; existing cards on `main` stay as history |
| `AGENTS.md` | the lines above `## Project landmines` become the v8 text; the landmines stay verbatim. Without that heading, `AGENTS.md` is untouched and `guard/AGENTS.proposed.md` holds the v8 text. |
| `guard/VERSION` | `schema: 8` |

`watch.list`, `guard/README.md`, `runs/_template/report.md`, `execution.tsv`, `FACTS.md` and `CLAUDE.md` do not change.

**GPU jobs on a launch host refuse until a person acts.** A migrated card keeps `max_gpu_hours: 0`, so every GPU job on a launch host refuses with H4R-R13 until a person raises the value in `guard/budget.card`. The update does not raise it, because the value is a spending decision.

**Receipts.** Set `broker_key:` before an agent cites a receipt. `guard init --update` writes this host's broker key when `guard broker setup` has run here; otherwise the line is a placeholder, and the fence refuses every receipt id with `no broker_key on main`. Protect the ref `guard/receipts` on GitHub as [enforceable.md](../enforceable.md#7-protect-the-guardreceipts-ref) says.

## Update a project from v7.0

```bash
# move the harness clone to v8.0, then propose the migration on a branch
git -C ~/harness4research fetch --tags && git -C ~/harness4research checkout v8.0
guard init <repo> --update
```

Read the diff, then push the branch and open its pull request. Pushing needs a token with the `workflow` scope, and a person merges it, because it changes `guard/` and the workflow.

A project at schema 6 or older moves to v7.0 first. `guard init <repo> --update` on it prints the command and stops:

```bash
# a v7.0 worktree of the same clone, then v7.0's migration; merge that pull request before the v8.0 update
git -C ~/harness4research worktree add --detach ~/harness4research-v7.0 v7.0
~/harness4research-v7.0/bin/guard init <repo> --update
```

Roll back by reverting the update pull request and checking the harness clone out at v7.0.
