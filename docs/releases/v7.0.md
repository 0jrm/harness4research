# Release v7.0

Guard schema 7. A guarded project now holds data, not code: `guard/bin/` is gone, and `guard/run` is a shim that runs the guard scripts from the harness at the release the project pins. A schema 6 project moves once, through `guard init --update`, in a pull request a person merges.

## What changes for a project

- **The pin.** `guard/budget.card` gains one line, `harness: v7.0`. The shim reads it from the default branch, never from the working tree, so a branch cannot change it.
- **Online hosts** run `lib/guard/<command>.sh` from the harness clone behind `guard` (or `HPC_HARNESS`), read from the pinned tag's objects with `git show`, never from the clone's working tree. The clone must be checked out at the pin; otherwise `guard/run` refuses and prints the `git -C <clone> fetch --tags && git -C <clone> checkout v7.0` to run.
- **Offline hosts**, where `guard init` cannot reach the harness's origin, get the scripts in one vendored file, `guard/harness-v7.0.sh`, read from the default branch. `guard init --online` or `--offline` chooses by hand. `guard version` and `guard doctor` say which mode a project runs in.
- **The fence workflow** reads the pin from the base branch and checks out `0jrm/harness4research` at it, so CI runs the same fence as the hosts.
- **Later updates are one line.** `guard init --update` on a pinned project proposes moving `harness:` to the clone's release, and, offline, swapping the vendored file.

## Changes since v6.2

- Scripts move to `lib/guard/`; the `guard/run` shim, the `harness:` pin and the online and offline modes (#117). The fence workflow runs at the pin (#120). The one-time migration in `guard init --update`; the three-way merge, the upgrade-from-each-release tests and `tests/oldest-supported` are removed (#121).
- `guard ship` runs at once when a records pull request is green, since that tier needs no model (#113).
- The evaluation's broker gains a records socket with signed ledgers and cards (#115), and a `gh` stand-in with review and merge in the broker (#118); the enforcement audit holds 53 of 56 rows.
- `tools/plan-status.py` generates `docs/status.md` (#114), and the audit's `hidden-data` row finishes on a CI runner (#119). Both affect the harness's own development only.
- `docs/compatibility.md` now lists only what stays stable; how the optional keys behave moved to `docs/guard-reference.md`.

## Update a project from v6.2

```bash
# move the harness clone to v7.0, then propose the migration on a branch
git -C ~/harness4research fetch --tags && git -C ~/harness4research checkout v7.0
guard init <repo> --update
```

The pull request changes exactly these files: `guard/budget.card` (one line added, `harness: v7.0`), `guard/bin/` (deleted), `guard/run` (replaced by the shim), `guard/VERSION` (rewritten), and `.github/workflows/guard-fence.yml` (replaced); offline, it also adds `guard/harness-v7.0.sh`. A site edit to `guard/bin/`, `guard/run` or the workflow is dropped, so read the diff first. Pushing it needs a token with the `workflow` scope, and a person merges it, because it changes `guard/` and the workflow. Card values, `watch.list`, `runs/_template/`, `FACTS.md` and `AGENTS.md` do not change.

After the merge, keep the harness clone at `v7.0` until the project's pin moves: an online `guard/run` refuses a clone at another release.

## Roll back

1. Revert the migration pull request on a new branch and merge the revert. Every branch and clone runs `guard/bin/` again after its next fetch, since `guard/run` reads the default branch.
2. Check out `v6.2` in the harness clone: `git -C ~/harness4research checkout v6.2`.
