# Release v6.0

Guard schema 6. Releases are tagged `vS.N`, where S is the schema (see [compatibility.md](../compatibility.md)). Schemas 2 to 5 shipped untagged. A clone at schema 5 calls itself `v1.1-<n>` in `git describe`.

This release answers the field report from the first install at an HPC site, FSU RCC, on 2026-10-13. That install ran `v1.1-181` (schema 5) and was rolled back to `v1.1-133` (schema 4). The sections below list what changed since `v1.1-181`, then summarize what a site still on `v1.1-133` also receives.

## Before you update

- **Runs in progress need merged domain checks.** After the update, preflight and launch refuse a run other than `explore-*` until the protected branch has an executable file in `runs/<id>/checks/`. To keep such runs going while the checks are written, a person adds `checks: waived <reason>` to `guard/budget.card` through a pull request. A run's question card is frozen, so it cannot add a waiver.
- **Merges may become manual.** Where GitHub offers the repository no rulesets, as for a private repository on the free plan, the update proposes `merge_policy: semi-manual`. `guard merge` refuses every merge without a ruleset, so a person merges each pull request.
- **Run `guard review` and `guard ship` where the reviewer CLI can reach the internet,** such as a login node. Run `guard doctor` there first. It now starts the reviewer once and names why it cannot answer.

## Changes since v1.1-181

### Review and merge

- A reviewer that exits nonzero, or replies nothing, no longer counts as an `escalate` verdict. `guard review` exits 2 with `reviewer unavailable:`, followed by the first stderr line that reads as an error and the path of the `.err` file. It records nothing and queues nothing. `guard review --batch` and `guard ship` skip the remaining reviews and exit 2 after their summary (#89).
- `guard doctor` starts each reviewer command once with a one-word task. It names the cause when none answers: not logged in, out of memory under the soft `ulimit -v`, no network, or no answer within `HPC_REVIEWER_PROBE_SECONDS` (default 120) (#96).
- Where GitHub offers no rulesets, `guard init` and `guard init --update` set `merge_policy: semi-manual` and say why, and `guard doctor` fails while the key stays `autonomous` (#90).

### Preflight and launch

- Preflight reads every form `sbatch` accepts for time, nodes and array, and refuses any option it cannot map exactly. It runs `squeue` and `sacct` from the budget card's `slurm_bin` (default `/usr/bin`) (#87).
- When `sacct` or `squeue` fails, preflight prints `accounting unavailable (sacct failed: …); not submitting` or `queue unavailable (…)`, instead of exiting with no FAIL line (#92).
- A run other than `explore-*` needs an executable domain check in `runs/<id>/checks/` on the protected branch, or `checks: waived <reason>` in its question card or the budget card. Launch applies the same gate (#97).
- The optional budget key `card_on_main: yes` holds a carded run until a person has merged its question card. The default is `no` (#98).
- Explore runs take the smaller of the explore cap and the project cap (#87).

### Ripples and the fence

- Ripples tells an unreachable accounting database from an off-cluster host and from a run with no jobs yet, and names sacct's first error line (#93).
- `runs/_template/execution.tsv` ships with the ledger's fields as comments. `guard fence --ledger <file>` checks a ledger before it is committed. A `void <id>` row retracts an agent's own wrong row in a pull request of run records only, unless the row sets a question card key (#94).
- `guard init --update` proposes the report template sections a project lacks, and the fence names a missing `## Execution history` section and the template that has it (#95).
- The fence freezes a question card even when one push adds and edits it, and protects `AGENTS.md` and `CLAUDE.md` like `guard/` (#87).

### Documentation

- `docs/compatibility.md` gains "Where each command runs": which commands need the internet, the reviewer's login, or the Slurm clients, and the notes on `ulimit -v`, process caps and command-routing hooks (#91).

## Also new for a site on v1.1-133

Schema 5 added these, and a site that rolled back has not run them:

- `guard review`, `guard merge` and `guard ship`, with path tiers, batched review, and `merge_policy` (#42, #44, #47, #48).
- The needs-you queue, `guard needs-you`, with commands rendered as one pastable block (#37, #61).
- Fixes: an unset `USER`; evidence paths must exist at HEAD; incidents count once merged; Slurm times by Slurm's grammar; the reviewer gets no stored `gh` login; `guard init` on NFS homes (#50, #51, #52, #56, #70).

## Install

On the site, in a branch of the project, after the usual backup:

```bash
# update the harness clone, then propose the guard update on a branch
git -C ~/harness4research fetch --tags && git -C ~/harness4research checkout v6.0
guard init <repo> --update
guard doctor <repo>
```

The update arrives as the branch `guard/update` in its own worktree. Read its list of changed files, keys and sections, then push it and open a pull request. A person merges it, because it changes `guard/`.

## Roll back

- **The project.** Revert the update pull request on a new branch and merge the revert. `guard/run` reads the protected branch, so every clone runs the old scripts after its next fetch, and the old `guard/VERSION` returns with it.
- **The harness.** Check out the previous release in the harness clone, for example `git -C ~/harness4research checkout <previous commit>`. `install.sh` links `guard` and the skills to the clone, so the links follow the checkout.
